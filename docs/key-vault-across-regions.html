Multi-region platform / Service Guides for Multi Region

Key Vault across regions

October 28, 2026 · 20 min read

Key Vault is often a runtime dependency: an application can need keys, secrets, and certificates just to start. Recovering data in another region is not enough if its key cannot be reached. Start with regional behavior, compare the products and patterns, then check the consuming service's requirements.

Secrets and Certificates management patterns

  • Pattern 1: Standard or Premium vault in each region
  • Pattern 2: Standard or Premium vault in a paired region

Key management patterns

  • Pattern 1: Standard or Premium vault with paired-region replication
  • Pattern 2: Standard or Premium vault in each region
  • Pattern 3: Premium vault per region with external HSM and BYOK
  • Pattern 4: Managed HSM with geo-replication
  • Pattern 5: Managed HSM geo-replication with external HSM and BYOK
  • Pattern 6: Managed HSM with external key management

Paired and nonpaired regions#

Paired regions. In eligible same-geography region pairs, Key Vault Standard and Premium replicate vault contents asynchronously to a Microsoft-managed secondary. That copy is part of the same vault, not a second vault you manage. Microsoft decides when to fail over; afterward, secrets, certificates, and keys are available read-only until normal operation returns.

Nonpaired regions. Do not assume a Microsoft-managed secondary exists. Use independent regional vaults when the consuming service supports them, or configure Managed HSM multi-region replication for keys. Managed HSM can extend to one supported additional region; it is not restricted to region pairs.

Important

Microsoft-managed failover is not supported for non-paired regions, regions with asymmetric pairing or paired regions across two different geographies.

See Microsoft-managed failover to a paired region for regional eligibility and Azure Key Vault security worlds for HSM cryptographic boundaries and backup/restore geography requirements.

When you plan a multi-region architecture on Azure, check how your target regions are paired. Pairing affects disaster recovery options, data replication and data residency.

1. Regions without a pair

In a region without a pair, choose a secondary region yourself and configure cross-region recovery for each service. Availability zones, where supported, provide resiliency within a region, not across regions.

2. Pairings that only go one way (asymmetric pairing)

A pairing isn't always reciprocal: a region's designated pair might not point back to it. Do not infer Microsoft-managed Key Vault failover support from a one-way pairing. Before you rely on built-in geo-replication, check each service's documentation for regional eligibility.

3. Pairs in different geographies

Some pairs cross geographic boundaries. A regional pair doesn't on its own keep your data within a particular country or geography, and it doesn't guarantee that every service replicates to the paired region. Key Vault is one example. Check data residency and service-level replication separately against your compliance requirements.

Microsoft-managed failover is best effort, not a customer-triggered recovery mechanism or a guaranteed application recovery time. Once initiated, public endpoint convergence is designed to take a few minutes; private endpoints can require up to an additional 20 minutes. Do not treat those routing timings as the total outage duration.

Failover guidance#

  • Microsoft-managed recovery: Keep using the same vault URI; Microsoft reroutes requests after failover. You cannot trigger this failover. Initiation can take hours or longer, independently of other services. Asynchronous replication means recent changes can be lost.
  • Read-only does not mean cryptography stops: After failover, supported actions include listing and getting keys, secrets, and certificates; encrypt, decrypt, wrap, unwrap, sign, verify; and backup. Creating, updating, renewing, rotating, or deleting objects is unavailable. Access policies, firewall settings, and vault properties cannot be changed.
  • Application readiness: Use SDK retries with exponential backoff and respect DNS TTL. Validate private connectivity from the recovery region; Private Link reconnection can add 20 minutes after failover. Monitor Service Health and Resource Health.
  • Customer-controlled recovery: Pre-provision independent regional vaults, identities, permissions, networking, and required object versions. Your application selects the healthy vault; a second vault alone does not provide fallback. Test recovery and return to the primary before production. Key Vault backups are point-in-time and restore only within the same subscription and Azure geography.

These are Standard/Premium vault behaviors. Replicated Managed HSM serves both regions; external keys have no geo-replicated failover target. See the official failover guidance and the key patterns.

Choose the product#

Key Vault is multi-tenant; Managed HSM is single-tenant. Keep the product choice separate from the regional deployment choice.

Secrets and certificates#

Use Standard or Premium vaults. Managed HSM and EKM do not store secrets or certificates. Compare the patterns, then review their distribution diagrams.

Pattern 1: Standard or Premium vault in each region#

  • Deployment: One Standard or Premium vault per workload per region, configured consistently through infrastructure as code (IaC).
  • Artifact origin: An approved secret-management process supplies secrets and certificates; the pipeline populates each regional vault.
  • During an outage: Each surviving region uses its own vault with full read and write access.
  • Best for: Workloads that need recovery independent of Microsoft-managed vault failover.
  • Watch for: Keep versions, renewal, access policies, identities, and private connectivity ready before an outage. Roll changes out sequentially, not globally at once.

Pattern 2: Standard or Premium vault in a paired region#

  • Deployment: One Standard or Premium vault in a region eligible for Microsoft-managed paired-region replication.
  • Artifact origin: The pipeline populates the primary vault; Microsoft asynchronously replicates its contents.
  • During an outage: Microsoft decides when to fail over. Afterward you can read, but cannot create, update, renew, or rotate objects until normal operation returns.
  • Best for: Workloads that can tolerate Microsoft-managed recovery timing and read-only access.
  • Watch for: Confirm the same-geography pairing, service exclusions, and recovery path rather than assuming any pair qualifies.

Treat each independent region as a deployment stamp. Do not store secret values in the IaC repository. Optional application-level fallback to another vault requires explicit identity, networking, and version-selection design; a second endpoint alone does not provide safe fallback.

Keys#

Customer-managed keys (CMKs) protect a service's data encryption keys; the data service still encrypts and decrypts the data. Bring your own key (BYOK) means importing externally generated key material. Here, BYOK refers to the supported HSM-to-HSM transfer process, not generic software-key import.

The six patterns below separate regional deployment from key protection. Standard supports software-protected keys; Premium supports HSM-protected keys. Both tiers share the same paired-region recovery model. The HSM-backed BYOK patterns use Premium or Managed HSM.

Pattern 1: Standard or Premium vault with paired-region replication#

  • Deployment: One Standard or Premium vault with an eligible Microsoft-managed paired-region copy.
  • Key origin: Generate the key in the primary vault. Use Standard for software-protected keys or Premium for HSM-protected keys.
  • Distribution: Microsoft replicates the same vault's contents; you do not create an independent secondary vault.
  • During an outage: Read-only key access after Microsoft-managed failover; no key creation or rotation until normal operation returns.
  • Best for / watch for: Services that accept Microsoft-managed recovery timing. Choose the tier for the required key protection and consuming-service support; Premium does not improve regional recovery control compared with Standard. Validate whether the application can meet its recovery objective.

Pattern 2: Standard or Premium vault in each region#

  • Deployment: One Standard or Premium vault per workload per region.
  • Key origin: Generate a separate key in each vault.
  • Distribution: No vault-to-vault replication; each service instance uses its configured regional key.
  • During an outage: Each surviving region retains full local read and write access.
  • Best for / watch for: Services that support independent regional keys. Do not apply this topology to a single GRS account or a shared-key dependency without service-specific support.

Pattern 3: Premium vault per region with external HSM and BYOK#

  • Deployment: One Premium vault per workload per region.
  • Key origin: A customer-owned external HSM.
  • Distribution: The BYOK process imports key material into each vault. This is not automatic vault-to-vault replication.
  • During an outage: Each surviving region uses its local imported key with full read and write access.
  • Best for / watch for: External key-origin requirements with independent regional vaults. Coordinate imports, versions, rotation, and consuming-service configuration. Pattern 2's service constraints still apply.

Pattern 4: Managed HSM with geo-replication#

  • Deployment: One Managed HSM pool with a primary and one supported extended region.
  • Key origin: Generate the key in Managed HSM.
  • Distribution: Asynchronous replication shares key material, roles, and permissions between regions.
  • During an outage: The healthy region continues serving reads and writes through the pool's endpoint.
  • Best for / watch for: Supported services requiring a shared key store and a customer-selected recovery region. Changes replicate within six minutes; recent changes can be lost if the primary is unrecoverable.

Pattern 5: Managed HSM geo-replication with external HSM and BYOK#

  • Deployment: The same primary/extended-region pool as Keys - Pattern 4.
  • Key origin: A customer-owned external HSM.
  • Distribution: Import the key into the primary pool through BYOK, then use Managed HSM geo-replication.
  • During an outage: The healthy region continues serving reads and writes.
  • Best for / watch for: External key-origin requirements plus replicated Managed HSM. Plan the import lifecycle and the same asynchronous replication window as Pattern 4; imported key material now resides in Azure HSMs.

Pattern 6: Managed HSM with external key management#

  • Deployment: Managed HSM, an EKM proxy, and your external HSM; no Managed HSM geo-replication for external keys.
  • Key origin: A customer-owned external HSM; the key encryption key never leaves it.
  • Distribution: Register an external key reference, not an imported copy of the key material.
  • During an outage: Recovery depends on Managed HSM, the proxy, external HSM, networking, or the region. There is no geo-replicated failover target.
  • Best for / watch for: A requirement for physical key custody outside Microsoft. Every external operation adds network round trips. No end-to-end Microsoft SLA covers the external components. Recreate an external key reference rather than attempting unsupported backup/restore.

For replicated Managed HSM, respect DNS time to live (TTL) so clients can reach a healthy region. Keep soft delete, purge protection, historical key versions, identities, and networking in the recovery plan. See multi-region replication, BYOK, and EKM scope and limitations.

Common key-management scenarios#

Each scenario lists candidate key patterns and the conditions for using them. Select a pattern name to return to its deployment details and diagram. Conditional means that the exact feature, topology, and key operations must satisfy the linked service guidance; it is not a blanket support guarantee.

Application-level encryption#

Your application decides whether each region uses an independent key or a common key. Preserve the key identifier and version needed to decrypt existing data. EKM is designed for compatible CMK encryption-at-rest integrations and exposes a restricted operation set; do not assume arbitrary application signing or encryption works unchanged. See key operations and external key lifecycle.

Patterns you can use:

  • Standard or Premium vault with paired-region replication: choose software-protected or HSM-protected operations and accept Microsoft-managed recovery timing.
  • Standard or Premium vault in each region or Premium vault per region with external HSM and BYOK: the application must handle independent regional keys or imports.
  • Managed HSM with geo-replication or Managed HSM geo-replication with external HSM and BYOK: use supported Managed HSM operations, including imported keys for BYOK.
  • Conditional: Managed HSM with external key management, only for supported external-key operations.

Azure Storage - Geo-redundant storage (GRS)#

GRS copies are replicas of one storage account, not independently configured accounts. Both depend on that account's CMK. Independent regional vaults do not let you assign a different key store to each GRS replica. Consider a replicated key store and test key access during account failover. See Storage CMKs.

Patterns you can use:

  • Standard or Premium vault with paired-region replication: both data copies depend on Microsoft-managed vault recovery.
  • Managed HSM with geo-replication or Managed HSM geo-replication with external HSM and BYOK: maintain access to the shared key.
  • Conditional: Managed HSM with external key management: verify Storage CMK integration and proxy availability; plan external-dependency recovery with no external-key geo-replication.

Azure Storage - Object replication for block blobs#

Source and destination are separate accounts, so their CMK configuration can be independent. Validate each account's identity, key versions, and recovery behavior. Do not carry GRS's shared-account constraint into this topology. See object replication.

Patterns you can use:

  • Standard or Premium vault in each region or Premium vault per region with external HSM and BYOK: source and destination accounts can use independent keys; for BYOK, import and authorize keys for each account.
  • Standard or Premium vault with paired-region replication: configure each account's key access and accept Microsoft-managed recovery.
  • Managed HSM with geo-replication or Managed HSM geo-replication with external HSM and BYOK: configure each account's CMK integration.
  • Conditional: Managed HSM with external key management, including recovery of the proxy and external HSM.

VM disk encryption#

For managed-disk server-side encryption, configure regional Disk Encryption Sets and key access. Managed disks and their key store must meet same-region requirements. This is different from guest-based Azure Disk Encryption and confidential VM key release. EKM does not support Secure Key Release. See managed-disk encryption.

Patterns you can use:

  • Standard or Premium vault in each region or Premium vault per region with external HSM and BYOK: configure regional Disk Encryption Sets and keys, including regional imports for BYOK.
  • Conditional: Standard or Premium vault with paired-region replication, Managed HSM with geo-replication, or Managed HSM geo-replication with external HSM and BYOK: satisfy the disk/key-store regional requirements, including imported key access for BYOK.
  • Conditional: Managed HSM with external key management, only for supported disk profiles that do not require Secure Key Release.

Azure Site Recovery#

Paired-region vault replication alone does not provision target-region encryption dependencies. Do not assume Managed HSM or EKM support from general managed-disk support.

Pre-create a compatible target-region Disk Encryption Set and authorize it to access its regional key vault. Include the source disks and cache storage account in the design. Site Recovery does not automatically apply encryption-key changes to protected VMs: the documented procedure requires disabling and re-enabling replication to adopt changes. Do not infer Site Recovery support from a general disk-encryption capability. See replication with CMK-enabled disks.

Patterns you can use:

  • Standard or Premium vault in each region: the documented regional-vault approach, with target-region Disk Encryption Set access.
  • Conditional: Premium vault per region with external HSM and BYOK: validate the imported key and complete Site Recovery configuration.

PostgreSQL and MySQL Flexible Server#

Distinguish read replicas, geo-redundant backups, and geo-restore. Their key, region, and identity requirements are not interchangeable. Provision recovery-region keys and identities as required; verify each product separately. See PostgreSQL encryption and MySQL encryption.

Patterns you can use:

  • Standard or Premium vault with paired-region replication: validate the product and recovery feature.
  • Standard or Premium vault in each region or Premium vault per region with external HSM and BYOK: meet regional key and identity requirements; for BYOK, validate key import for the recovery feature.
  • Managed HSM with geo-replication or Managed HSM geo-replication with external HSM and BYOK: confirm Managed HSM support and regional requirements for that feature, including BYOK import where used.
  • Managed HSM with external key management: verify the service's external-key CMK integration and the recovery feature separately.

Azure SQL Database, Azure SQL Managed Instance and Azure Cosmos DB geo-replication#

SQL Database and SQL Managed Instance need the required TDE protector keys available to their replicas. Documented SQL designs can use regional copies of key material; rotation must preserve access to every required version. Cosmos DB uses an account-level CMK dependency and has its own networking and key-store requirements. Do not assume SQL's key-copy design applies to Cosmos DB. Replicated Managed HSM is a candidate where supported; compare its cost with the accepted risk of Microsoft-managed vault recovery, not an arbitrary number-of-keys threshold. See SQL customer-managed TDE and Cosmos DB CMKs.

Patterns you can use:

  • Managed HSM with geo-replication or Managed HSM geo-replication with external HSM and BYOK: candidates for supported shared-key dependencies; with BYOK, manage the imported-key lifecycle.
  • Standard or Premium vault with paired-region replication: accept the Microsoft-managed recovery risk and preserve replica key access.
  • Standard or Premium vault in each region or Premium vault per region with external HSM and BYOK: only with a documented service-specific key-copy and rotation design, not as a general shared-key solution.
  • Managed HSM with external key management: verify the exact integration; external keys have no geo-replicated failover target.

Azure SQL Database, Azure SQL Managed Instance and Azure Cosmos DB geo-restore#

Restoring data does not restore access to its encryption keys. Retain all historical keys required by the backup, authorize the restored service, and verify the target region/geography against that service's restore rules. A fresh key in a new vault is not a substitute. There is no single cross-geography rule that can safely represent every SQL and Cosmos DB restore feature. See the SQL recovery requirements and the Cosmos DB CMK requirements.

Patterns you can use:

  • Standard or Premium vault with paired-region replication: the restore target must retain access to the original keys.
  • Standard or Premium vault in each region or Premium vault per region with external HSM and BYOK: preserve the required key material and versions; newly generated regional keys cannot replace them.
  • Managed HSM with geo-replication or Managed HSM geo-replication with external HSM and BYOK: verify service restore support and historical key availability.
  • Managed HSM with external key management: retain the original external key and reference; external-key backup/restore is not supported.

Purview Information Protection#

Identify whether the requirement concerns an Azure Rights Management tenant key, Microsoft 365 Customer Key, or another protection feature. These are not interchangeable integrations. For tenant-key BYOK, the documented Premium-vault approach imports an external HSM key into Azure; it is not direct real-time use of an on-premises HSM. Preserve keys that protect old content and test recovery before production. Consider Microsoft-managed keys unless customer control is required. See Rights Management BYOK.

Patterns you can use:

  • Standard or Premium vault with paired-region replication, using Premium: the documented HSM-backed vault option; preserve keys for old content. Standard software-protected keys require feature-specific confirmation.
  • Premium vault per region with external HSM and BYOK: use its external-HSM import approach with a dedicated Premium vault. Do not treat Microsoft 365 as a regional deployment stamp.

Other options require feature-specific confirmation: Managed HSM with geo-replication, Managed HSM geo-replication with external HSM and BYOK, and Managed HSM with external key management. Confirm the exact feature's key lifecycle, Managed HSM/BYOK configuration, or supported external-key operations, as applicable. An independent-vault workload stamp is not applicable to this tenant-level service.
