Profile 1 of 4

Workload spokes in the new region do not require platform shared services, can operate without a private network path to a more strategic region, and/or to an on-premises environment. They could still use direct connectivity to other spokes where required and approved private or public connectivity to Azure platform services. The subscriptions in this new region are still governed from a Management Group, Policy and RBAC standpoint.

Fits when
Workloads can operate without shared platform services, private connectivity to a more strategic region, and/or to an on-premises environment, and their required platform capabilities can be consumed globally or through approved Azure service connectivity, such as public or private endpoints, and without any dedicated regional platform resources. This can include self-contained cloud-native, AI, development, test, batch, HPC, VDI, or internet-facing workloads where those conditions are met.
Regional footprint
Workload resources plus the controls needed to deploy, secure, monitor, and operate them. These spokes still use the estate’s standard identity, policy, security, and deployment practices.
Key considerations
Validate administration, identity, DNS, secrets, telemetry, data movement, software distribution, private endpoints, incident response, and support procedures. Where applications require east-west communication within the region, evaluate direct spoke-to-spoke connectivity without assuming that a local network hub is required. Confirm that no hidden dependency requires connectivity to a Full-Platform region or on-premises environment.
Reassess the profile when
Workloads require a Full-Platform region, on-premises connectivity, centralized inspection, or private network paths beyond approved same-region spokes and Azure service endpoints.

{{PROFILE_2}}

Profile 2 of 4

Workloads in the new region use cross-region connectivity to consume platform services from an existing more strategic region. A more strategic region can provide connectivity to on-premises environments, traffic inspection, internet egress, routing, DNS, identity, monitoring, and other shared platform services.

Cross-region connectivity can be implemented through appropriate Azure networking capabilities based on the required topology and routing model, usually Global Virtual Network peering, Virtual WAN Virtual Network Connection, or Azure Virtual Network Manager. Public application ingress can remain local through services such as Azure Front Door and/or Application Gateway when appropriate.

Fits when
Workloads require private access to selected enterprise or on-premises services but can tolerate the latency, availability coupling, data-transfer implications, and dependency on connectivity to another region.
Regional footprint
Workload spokes and any capabilities that must remain close to the workloads. Gateways, firewalls, routing resources, and other platform resources can remain in a more strategic region when workload requirements permit.
Key considerations
Measure latency and bandwidth using representative traffic. Evaluate cross-region data-transfer cost, routing and transit behavior, inspection paths, Full-Platform region scale, dependency criticality, and operational ownership. Document how workloads behave if the Full-Platform region or cross-region connectivity is degraded or unavailable.
Reassess the profile when
Cross-region traffic, latency, east-west communication, dependency criticality, regulatory requirements, scale, or availability coupling justify deploying selected connectivity or shared-service capabilities locally.
